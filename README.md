# Medusa module clone in Go

This Go/Gin service ports selected Medusa modules and workflows from `D:\my-project\open-source-medusa`. Source matching rules live in [AGENTS.md](AGENTS.md); the reusable clone workflow is in [.agents/skills/medusa-module-cloning/SKILL.md](.agents/skills/medusa-module-cloning/SKILL.md).

## Run

Requires Go 1.23+ and PostgreSQL with the required schema already present. API startup does not run SQL migrations; apply numbered migrations separately when you choose to update the schema.

To start the API, Admin, and Storefront in separate Windows PowerShell windows, run `./run-apps.ps1` from the repository root. Use `./run-apps.ps1 -InstallDependencies` to install frontend dependencies first when either app has no `node_modules` directory. The script reads API settings from the root `.env` file when present.

```powershell
$env:DATABASE_URL = "postgres://root:root@localhost/my-db?sslmode=disable"
$env:JWT_SECRET = "use-a-long-random-value"
go run ./cmd/api
```

The default listen address is `:8080`. The app does not load `.env` files automatically.

The Inventory reservation lock provider defaults to process-local memory. Set `LOCKING_PROVIDER=postgres` to use the PostgreSQL provider; this requires the authored `025_locking_postgres.sql` schema to have been applied separately. Set `LOCKING_PROVIDER=redis` with `LOCKING_REDIS_URL` to use the Redis provider; optional settings are `LOCKING_REDIS_NAMESPACE`, `LOCKING_WAIT_TIMEOUT_SECONDS`, `LOCKING_DEFAULT_RETRY_INTERVAL_MS`, `LOCKING_MAXIMUM_RETRY_INTERVAL_MS`, and `LOCKING_BACKOFF_FACTOR`. Notification delivery defaults to local logging; set `NOTIFICATION_PROVIDER=sendgrid`, `SENDGRID_API_KEY`, and `SENDGRID_FROM` to use SendGrid. Analytics defaults to local logging; set `ANALYTICS_PROVIDER=posthog` and `POSTHOG_EVENTS_KEY` to use PostHog, with optional `POSTHOG_HOST` (default `https://eu.i.posthog.com`). File storage defaults to local; `FILE_PROVIDER=s3` selects S3 with `S3_BUCKET`, `S3_REGION`, `S3_FILE_URL`, and access-key credentials (`S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`) or `S3_AUTHENTICATION_METHOD=s3-iam-role`. Optional S3 settings are `S3_SESSION_TOKEN`, `S3_PREFIX`, `S3_ENDPOINT`, `S3_CACHE_CONTROL`, `S3_DOWNLOAD_FILE_DURATION` (seconds), `S3_ACL` (including `false` to omit ACL), and `S3_USE_PATH_STYLE=true`. API startup never applies migrations.

The Admin dashboard defaults to the Go API at `http://localhost:8080/api/v1`. The API allows browser requests from `ADMIN_CORS` and `STORE_CORS` origins (defaults `http://localhost:7001` and `http://localhost:8000`). The dashboard initialization routes for auth providers, feature flags, and cloud auth are present; other Admin endpoints remain unported.

## Module and workflow structure

- `internal/modules/{api-key,auth,customer,links,region,sales-channel,stock-location,store,user,currency,rbac,product,settings,notification}` follows DDD boundaries: module models and ports under `domain`, use cases under `application`, and Postgres/security adapters under `infrastructure`.
- `internal/coreflows/customer/workflows` implements account creation in Medusa order: validate, create customer, optionally publish `customer.created`, then set auth metadata. The event publisher is optional because event-bus wiring is not yet part of the running API.
- `internal/coreflows/{region,sales-channel,store,user}/workflows` contains direct create functions with Medusa workflow and step IDs. Region creation runs payment-provider validation/linking, price-preference creation, and event emission through ports; user creation validates RBAC roles, creates user-role links, then emits `user.created`. Store currency pricing and workflow events use ports.
- Migrations `007_admin_domain_modules.sql` and `008_links.sql` add store/currency/locale, user/invite, sales channel, region/country, and the writable Medusa link-definition tables. The country seed follows Medusa's default country dataset.
- Migration `009_currency_rbac.sql` adds the normalized currency catalog and RBAC roles, policies, role-policy/parent relations, default currency seed, and Medusa's super-admin records.
- `internal/coreflows/rbac/workflows` ports role, policy, and role-policy creation with source workflow IDs, source ordering, actor permission validation ports, and compensation for failed later role steps.
- Migration `010_product_module.sql` adds the Medusa product, variant, option/value, type, tag, collection, category, image, and association tables. `internal/coreflows/product/workflows` implements the create-products path, including option validation, sales-channel and shipping-profile links, and product-created event emission.
- `internal/modules/api-key` and `internal/coreflows/api-key/workflows` implement Admin API key creation (publishable plaintext and scrypt-hashed secret tokens), list/retrieve/update/revoke/delete, and publishable-key sales-channel links. Migration `012_api_key.sql` adds the API key table; startup does not execute migrations.
- `internal/modules/fulfillment` implements fulfillment sets, service zones, geo zones, shipping options/rules, and fulfillment execution. The stock-location association workflow preserves `create-location-fulfillment-set`; Admin fulfillment create/cancel/shipment use direct source workflow IDs, provider calls, fulfillment address/item/label persistence, and source event names. Migrations `020_fulfillment.sql`, `031_shipping_option.sql`, and `032_fulfillment_records.sql` are authored but have not been executed. Remaining fulfillment gaps include complete order fulfillment orchestration/notifications, route query filters, and exact query-graph field semantics.
- `internal/modules/order` currently implements Medusa-shaped order/address/line-item/summary read models and source-ID `get-orders-list` / `get-order-detail` functions, exposed through Admin and Store list/detail routes. Admin archive uses `archive-order-workflow` / `archive-orders`, validates allowed statuses, and buffers `order.archived` until the update succeeds. Admin completion uses `complete-order-workflow` / `complete-orders`, rejects canceled orders, and restores prior statuses if event publishing fails. Admin update uses `update-order-workflow`, `update-order-validation`, `find-or-create-customer`, `update-orders`, `register-order-change`, and `preview-order-change`; it preserves country-code restrictions, creates or resolves a Customer when an order without an email receives one, compensates newly created Customers if the order update fails, stages `customer.created` with `order.updated`, and records confirmed order-change actions. Admin claim list/detail/create/delete routes use the `order_claim` model. Claim creation follows `begin-claim-order`, validates canceled order state, creates the claim then a pending order change, and soft-deletes the claim if order-change creation fails. Claim deletion follows `cancel-begin-order-claim` / `validate-cancel-begin-order-claim`, removes its active order change and claim, and restores nothing after success. Claim items and images have source-shaped DDD read models and authored persistence; detail reads populate additional and claimed items. Claim item writes, replace-type return creation, shipping-method cleanup, module events, and claim action workflows remain incomplete. Migration `021_order.sql` and `029_order_claim.sql` are authored but have not been executed. Locale translation refresh, cancellation/payment refunds/reservation cleanup, order creation, fulfillment/payment flows, returns, exchanges, transfers, export, full field projection, and the remaining Order routes/workflows are not yet ported.
- `internal/modules/stock-location` and `internal/coreflows/stock-location/workflows` implement location/address CRUD, sales-channel linking, and the fulfillment-set association workflow with Medusa workflow IDs. Migration `013_stock_location.sql` defines location/address persistence. Event-bus publication and fulfillment-provider relationships remain outside the Go implementation.

The API route audit is incomplete against the full Medusa route tree. Current gaps by module:

- **Auth:** email/password register/login and provider discovery are exposed. Provider discovery is mounted on Medusa's explicit `GET /auth/:actor_type/providers` route and includes configured `emailpass`, GitHub, Google, and OIDC providers. GitHub and Google OAuth start and GET/POST callback use source state semantics (random state and 1200-second one-use cache) and provider-specific token exchange. Google verifies the ID token RS256 signature using cached Google JWKS, issuer, audience, expiration, verified email, and subject. The OIDC provider accepts source-shaped JSON in `AUTH_OIDC_CONFIG`; it supports discovery and endpoint overrides, PKCE S256, nonce, callback allowlists, token/JWKS verification, email policies, and claim mappings. OIDC uses the source 600-second state default; OAuth state currently uses the host's process-local `cache-inmemory`. A successful login with an enabled factor returns Medusa's `{mfa_required, mfa_challenge, token}` response; the bearer token remains actorless and has `mfa_enabled=true` until `POST /auth/mfa/challenges/:id/verify` succeeds. Challenges preserve the `auth:mfa:challenge:<id>` key, five-attempt and 300-second defaults, supported-method checks, single-use completion, TOTP/recovery-code verification, and final token claims. `AUTH_MFA_CHALLENGE_TTL_SECONDS` and `AUTH_MFA_CHALLENGE_MAX_ATTEMPTS` configure limits. The host currently wires the Medusa-compatible `cache-inmemory` provider, so challenge and OAuth state are process-local and do not support multi-instance verification. Medusa's configurable `authVerificationsPerActor` gate is not wired yet, so Go does not return `verification_required` before actor-token issuance. `POST /auth/token/refresh` reloads actor-linked auth identity/provider metadata and issues a fresh token while preserving MFA claims; actorless refresh (which must repeat MFA/verification checks) is not implemented. Token `POST /auth/verification/request` and `/auth/verification/confirm` preserve `request-verification-workflow` / `request-verification`, source token hashing and 15-minute expiry, scoped single-use confirmation, and `auth.verification_requested` payload behavior. `POST /auth/:auth_provider/user` follows the source actorless identity checks, enforces that the identity has exactly the route provider, links an existing Admin user by provider-verified email, or invokes `create-user-account` / `create-users-workflow` and `set-auth-app-metadata`. TOTP factor list/start/verify/disable routes preserve source states, AES-256-GCM secret format, RFC 6238 SHA-1 codes and lifecycle events. Recovery-code generation replaces prior codes with source scrypt hashes and IDs; challenge verification consumes one code exactly once. Set `AUTH_MFA_ENCRYPTION_KEY` before starting TOTP enrollment. `POST /auth/:actor_type/:auth_provider/reset-password` returns 201 whether or not a reset token can be issued; `/update` validates and consumes the single-use reset token before updating the provider password. Reset tokens are hashed and emit `auth.password_reset`. Session create/delete, multiple OIDC registrations, actor-specific provider allowlists, non-token verification providers, source `authVerificationsPerActor` enforcement, and MFA/verification enforcement during actorless refresh remain incomplete. No migration was run.
