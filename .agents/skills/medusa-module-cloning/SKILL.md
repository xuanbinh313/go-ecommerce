# Medusa module cloning

Use this skill when cloning or extending modules and their APIs in `microservices-app` from `D:\my-project\open-source-medusa`, including API key, auth, customer, links, store, user, sales channel, region, currency, RBAC, product, settings, and notifications.

## Workflow

1. Inventory every source API route for the selected module before implementation. Record method, path, middleware/authentication, validators, query handling, request fields, response shape, and error behavior. Include auxiliary routes such as provider discovery, callbacks, sessions, reset flows, and feature metadata, not only CRUD routes.
2. Identify the source models, services, workflows, and steps behind those routes. Trace callers and dependencies. For workflows, record ordered steps, values passed between them, and compensation required when a later step fails.
3. Port each module into DDD layers: entities and ports under `internal/modules/<module>/domain`, use cases under `application`, and Postgres adapters under `infrastructure`. Put all corresponding HTTP handlers under `internal/api` and workflow functions under `internal/coreflows`.
4. Implement every in-scope source route and method, including its middleware/authentication, validators, query behavior, request and response fields, status codes, and errors. Preserve Medusa field names, IDs/prefixes, route paths, uniqueness rules, soft-delete behavior, and failure behavior. Do not mark a module or endpoint set complete while routes are missing. Do not invent a more convenient alternate structure.
5. Port workflows as direct functions that call module domain interfaces in source order and apply the source compensation behavior on errors. Do not add a separate orchestration engine or workflow execution table.
6. Review the source-to-Go route inventory after implementation. Make missing routes explicit in the README or final status, distinguishing unsupported dependency behavior from endpoints that have not yet been ported. Do not imply full parity when either remains.
7. For an all-modules clone, enumerate every directory under `packages/modules` and every route under the matching `packages/medusa/src/api` scope. Record Go mappings where package names differ (for example, `link-modules` to `links`), then repeat the inventory after implementation. A folder stub or a passing build does not count as a cloned module.
8. SQL migrations may be authored as numbered files, but never execute SQL or apply migrations as part of clone/startup work. Runtime startup must not apply migrations implicitly.
9. For a request to clone all modules, include every module folder under `packages/modules`, including infrastructure modules such as providers, cache, locking, index, workflow engines, and event buses. For each, record whether it has Medusa API routes; modules without routes still require their service behavior and dependencies to be inventoried. Do not treat a module as complete just because a same-named Go folder exists.
